# 基础开发规范

在首次修改代码前读取本规范，并在实现过程中持续遵循。项目明确约定和目标语言惯例优先；若与用户合同冲突或关键业务语义未确认，先澄清。示例中的代码形态为伪代码，不规定任何语言的具体语法。

## 命名

### G-01 名称必须指出它代表的业务角色

按含义命名变量、参数、字段、函数和模块，让读者能分辨相近概念。宽作用域中的 `data`、`value`、`result`、`info` 不足以区分订单、原始请求、已验证记录或统计结果；当上下文不能立即补足时用具体角色命名。局部表达式里显然的临时值可短命名。

### G-02 采用项目通用的英文术语，谨慎使用缩写

名称用项目既有领域词汇，不逐字翻译中文后创造生硬新词。只缩写团队普遍理解且在邻近代码一致的术语；自造首字母缩写、截断单词或同一缩写多义时写全。语言若允许大小写首字母同时存在的导出形式，应遵循该语言惯例，避免只靠大小写制造易混名称。

反例（伪代码）：`usrCfg`、`procRes` 在新模块里没有约定，读者需猜含义。可读写 `userConfig`、`processedRecords`。对于行业通用缩写，不为形式统一强行展开。

### G-03 布尔名称要表达正向判断

布尔名称表达某个事实或是否满足条件，如 `isExpired`、`hasPermission`、`shouldRetry`。优先避免 `isNotReady`、`disableCheck` 等双重否定或否定选项；若 `disabled`、`failed` 等本身就是领域状态，或旧协议字段固定使用否定形式，应保留其真实含义，不擅自改协议。调用处应能自然读出条件真假。

### G-04 查询名称与动作名称必须区分

只读取或计算结果的函数名表达返回信息；改变状态、发送命令或写入的函数名表达动作。查询可以因读取而访问网络或存储，不要求把 `getUser` 改成 `loadUser`；其公共合同应说明重要的成本、失败方式和资源要求。不要用 `get`、`check` 等查询名称掩盖写入、发送命令等非查询副作用，也不要让调用方误以为查询会修改状态。

### G-05 集合名称应说明成员类型或业务角色

集合名用复数或项目惯用集合词，并让成员角色可辨，例如 `pendingOrders` 表示待处理订单。不要用单数泛名 `item` 装整个列表，也不要依赖变量名暗示集合有序或已去重；顺序和重复语义须由实际类型/合同保证。

### G-06 名称应携带重要单位和时间基准

凡单位会影响运算、比较、配置或协议解释，名称或类型必须表达单位；时间需区分时刻、日期、持续时长及其基准。`timeout` 若可能是毫秒、秒或截止时刻，应改为明确单位/语义或使用可区分类型。跨边界转换时在边界完成并保持值和单位对应。

伪代码：`timeoutSeconds` 与 `deadlineAt` 含义不同；不能把二者都叫 `timeout`。`amountCents` 只在合同确实以分存储时才比 `amount` 合适。

### G-07 短局部名只用于短且单一的作用域

`i`、`j` 等循环索引以及短回调参数在几行内用途单一时可用；若变量跨多个分支、步骤或闭包存活，就用角色名。不要给临时变量逐个造无语义的新名，也不要让省略写法迫使读者追踪多层上下文。

### G-08 避免同一作用域中遮蔽仍有用的名称

内层变量、参数或导入不得遮蔽外层仍需区分的值，尤其是错误、上下文、请求和资源句柄。确需复用名称时，确认外层值之后不再使用且语言语义不会改变闭包或延迟读取的结果。不要以缩短变量名为由重用名称表示不同阶段的数据。

## 常量与配置

### G-09 为可复用策略值命名并集中其来源

在多处使用、需要共同调整或具有业务含义的值提取为有语义名称；部署或用户可调策略从项目已有配置合同读取。配置默认值、范围和单位应与合同一致，不能复制成多个互不一致的字面值。

### G-10 单次显然的结构性字面值可以内联

不要把所有 `0`、`1`、空串或布尔值机械提升为常量。若值只出现一次、语境清楚且不是可调策略或领域规则，直接写清楚即可。将 `0` 命名为 `zero` 不会增加含义；把多个语义相同的重试上限写成有名称的配置则能表达策略。

## 函数与表达式

### G-11 一个函数应完成一个可陈述的工作

围绕单一结果组织函数；解析、授权、决策、持久化等阶段若有独立合同或失败处理，应能分别看清。不要为了行数短拆成一串仅转发参数、没有独立含义的函数；也不要因“都属于处理”把多个独立副作用塞进同一入口。

### G-12 参数应代表调用者确有必要提供的信息

仅传递完成该职责需要的输入。不要把同一对象的大量字段拆成参数再在函数内拼回去；若参数确实共同构成一个领域概念，使用项目已有类型表达。参数很多时先检查职责是否混杂，不要仅为减少签名长度造万能 options 包。

### G-13 布尔 flag 不得暗中切换两种工作模式

若一个布尔参数改变函数做什么、写哪里或采用何种错误语义，应拆成能表达两种动作的入口，或改用能明确命名模式的领域类型。只有参数确实是该操作的普通开关且调用点可读时才保留。

反例（伪代码）：`save(record, true)`，调用点无法知道 true 表示覆盖、发布还是跳过校验。清晰入口或具名选项能让语义可见。

### G-14 调用路径应保持一致的返回合同

同一个函数的成功路径应返回同一种概念的结果，失败路径按项目机制显式返回/传播。不要有时返回原对象、有时返回布尔、有时返回空值表示失败；不要把“未找到”“输入无效”和“系统失败”塞进无法区分的空值。合同确实允许可选结果时，明确其缺失含义。

### G-15 让副作用从函数名、签名或类型可识别

读写外部状态、发送、记录、修改共享对象或申请资源属于副作用，须在合适边界显现。计算或解析逻辑适合单独表达时，不要让它暗中读取全局状态或发起 I/O。无需为简单、局部的副作用另建抽象层。

### G-16 失败前置条件可在正常路径前处理

无效输入、拒绝或错误条件可在函数前段返回/传播，使正常路径少嵌套；但必须保留资源清理、错误优先级和状态更新顺序。提前返回不得跳过必要副作用或把“暂时未完成”误作成功。没有固定行数限制，以控制流易读为准。

### G-17 复杂条件拆成具名事实且不改变求值语义

同一业务判断由多个条件组合且难以一眼读懂时，为稳定的中间事实命名，并说明条件代表的业务含义。拆分时保留原短路顺序：可能报错、产生副作用或访问无效值的子表达式不得提前执行。简单的两项条件无需逐项命名。

伪代码：若 `record != null && record.isActive()` 依靠短路避免空引用，不能先无条件计算 `isActive = record.isActive()` 再判断。仅对纯安全判断可提取具名布尔事实。

## 模块与复用

### G-18 先在拥有该职责的模块局部实现

新增逻辑放在现有职责边界最接近、且拥有所需数据或副作用的位置。不要为了使用新抽象把一次性逻辑搬离调用现场；也不要让业务规则落在低层通用模块，迫使底层反向依赖具体业务。

### G-19 抽象要对应稳定共性或隔离变化点

只有多个调用方具有相同语义，或独立封装能隔离真实变化原因时才共享实现。共享抽象需统一输入输出、失败、权限、资源和副作用合同。相似代码若业务含义或演进方向不同，应保留局部实现，而不是用参数开关把差异藏进万能函数。

### G-20 优先组合小能力，不造万能工具层

组合职责清楚且已存在的能力；新抽象须让调用关系或合同更清晰。不要为单次调用新增 `CommonUtils`、万能管理器或只有一层转发的包装。重复几行简单代码可以接受；重复导致行为漂移或多个调用者需要同步修改时，再提炼稳定共性。

### G-21 依赖方向应指向被使用的稳定能力

高层策略可调用低层通用能力，通用模块不应导入具体业务来完成反向决策。跨边界所需的接口/回调遵循项目语言惯例，并只在替换实现、隔离外部系统或稳定模块边界确有必要时引入；不要求每个服务类都抽接口。

## 数据与状态

### G-22 缺失、null、空值和零只有在合同等价时才能合并

检查外部与内部表示是否需区分字段不存在、显式 null、空集合、空字符串、零值和解析失败。只有合同说明等价时才归一；不得把缺字段默认为零来掩盖损坏数据。适用默认值必须有已确认来源，并与错误路径区分。

### G-23 状态集合及转换必须受合同约束

状态应使用有限且可识别的表示；状态切换在改变持久数据或对外可见行为的边界校验前置条件。新增状态、转换或非法状态处理需来自需求或既有合同，不自行发明“其他状态都当成功”。

### G-24 不允许的状态组合应无法形成或在边界被拒绝

若多个标志可以形成互相矛盾的组合，优先用互斥状态表示；若兼容原因必须保留多个字段，在读取/写入边界检查组合并定义错误处理。不要靠注释声称某组合“不会发生”，却在运行时允许它进入核心流程。

### G-25 集合类型要符合查找、顺序和重复语义

按用途选择序列、集合或映射：索引访问/有序遍历、唯一成员或键查找各自需要不同语义。构造、过滤或合并集合时保留合同规定的顺序与重复；不得假设无序映射稳定排序，也不得擅自去重或排序可观察结果。

### G-26 金额运算必须使用合同规定的精度和舍入点

选用与金额精度相符的表示并携带币种或合同规定的单位。累计、换算、展示和持久化应明确舍入策略及发生位置，避免每一步悄悄截断或使用不适合精确金额的浮点近似。若领域未说明精度、币种或舍入方式，先澄清，不作默认决定。

### G-27 时间点、日期和时长应使用不同语义

区分绝对时刻、当地日历日期、时长和截止时刻。跨系统保存/传递或跨进程/重启共享截止时间时，遵循明确的绝对时间及时区合同；本地日历规则按合同使用指定时区，不能假定所有一天恒为固定秒数。进程内测量耗时和超时使用单调计时，避免墙上时钟调整导致时长倒退；需要持久化或共享的 deadline 则使用可跨进程比较的绝对时间并明确精度。协议转换在边界完成并保留精度。

### G-28 可变对象需明确是否与调用者共享

函数接收或返回可变数据时，确认调用者修改是否影响内部状态及其他持有者。需要独立快照时，复制相关可变部分，或使用确有快照保证的不可变表示；仅限制调用者写入时可提供只读接口，但它不保证独立快照，底层别名和源数据变化仍按合同说明。不要让调用者无法判断别名关系，也不对大型对象无差别深拷贝。

## 注释与维护

### G-29 对外入口应说明调用者必须遵守的稳定合同

公共 API、配置项或模块边界的说明应描述必要的前置条件、结果语义、副作用、资源所有权及重要失败情况。只写签名已清楚表达的内容无需重复；合同改变时同步更新说明。采用语言/项目惯用文档位置和格式，不机械要求 Javadoc 等特定风格。

### G-30 行内注释解释非显然原因和约束

用注释说明为什么采用不直观做法、兼容限制从何而来、某失败如何处理或一个算法约束是什么。不要逐行复述显然代码；实现改变后更新或删除失效注释，不能让注释保留旧合同。

### G-31 格式服从项目现有工具和约定

使用仓库已有 formatter、linter 及代码风格；若未配置，匹配同目录相邻代码。修改只触及必要行，避免将格式化差异混入行为变更。通用规范不统一规定各语言缩进、行宽、命名大小写或导入排序。

### G-32 修改范围和兼容判断依据真实调用方

检查本次变更的实际调用者、输入输出、错误、数据格式和副作用合同，只改完成目标所需部分。公共 API、配置、持久化格式或既有行为变化前确认迁移与兼容要求；不要顺手重构邻近代码。没有明确合同的业务默认值、权限策略、单位或回退行为需澄清。

### G-33 验证断言必须证明用户目标或既有合同

为变更中可观察的要求选择足以证明它的验证方式；断言覆盖相关的正常、边界及失败行为，不只检查内部函数调用或实现细节。按风险选单元、契约或集成验证；当已有隔离验证足够时不机械增加端到端测试。记录实际运行结果，区分未执行和未验证边界。
