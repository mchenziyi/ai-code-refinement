# 并发与持久化

实现共享状态、并发任务、重试或多步写入前读取；没有相应风险时不套用额外机制。

## C-01 为完整读改写不变量提供协调

若操作先读取/判断再修改共享状态，锁、事务、原子比较交换或版本条件必须覆盖整个决策及更新；只保护单独读写仍会丢失更新。冲突时按现有合同重读并重新计算，不以旧读值覆盖新状态。单所有者本身能保证串行时，不额外加锁。

## C-02 固定锁定顺序并缩短临界区

需要同时持有多把锁时，所有相关路径遵循同一顺序以避免死锁；临界区只覆盖保护不变量所需操作，避免无关或不可控等待。确有合同要求在持锁期间完成 I/O（例如需维护文件写入顺序）时，明确阻塞影响、错误路径和退出清理。可在锁外准备的长工作应移出，再在锁内校验版本并提交。

## C-03 并发组合须明确其余任务的结束状态

组合多个并发任务时，依据实际 API 处理一项失败后其余任务是否继续、是否请求取消及如何收集其结果/错误；一个任务失败不代表其他任务已自动终止。不要 fire-and-forget 后假定失败会自动传到调用者。

## C-04 对无界输入或慢消费者设容量与背压

队列、并发工作和缓冲区在规模未知或输入持续时需有边界，容量满时选择等待、拒绝或合同允许的丢弃，并使上游能感知结果。记录可观察的拒绝/丢弃状态，避免静默丢失。有限且受控的小批量任务不需额外队列或全局并发框架。

## C-05 重试须符合操作幂等合同

每次重试之前确认错误可重试、最大尝试、截止时间及结果未知时的恢复方式。幂等键代表同一逻辑操作，应在该操作全部重试中保持相同；每次重试新建 key 会让服务把重复请求当新操作。确认服务对键的作用域、有效期和相同键载荷一致性要求，超出其保护范围时用查询/对账等合同机制处理。只有新业务操作才生成新 key。HTTP 方法或本地函数名不能代替业务副作用合同判断。

伪代码：先为 `charge(order)` 生成一次 `operationKey`，超时后用同一 key 查询/重试；不得在循环体里每次随机生成 key。

## C-06 重试要受时间边界和系统策略约束

总重试窗口不能越过调用者截止时间或业务有效期；避免无上限次数和紧密忙循环。退避、抖动及可重试类别使用项目既有策略。副作用已成功但响应丢失时，优先按合同查询或对账，而非假定未执行。

## C-07 多步写入定义中间状态和恢复动作

列出步骤、成功判定及每步可能已生效的结果。按存储能力选择事务、原子替换、补偿或显式可恢复状态；跨服务不假设本地事务能覆盖远端。若恢复/补偿本身失败，状态须能被识别和重试或人工处理，不能报告整体成功。

## C-08 原子可见性不等于断电持久化

原子重命名等机制可避免读者看到半个文件，但不自动保证数据与目录项在断电后都已持久化。只有需求有崩溃持久性要求时，按目标平台和文件系统合同执行文件及目录同步等步骤；不将特定操作系统 API 无条件套用到跨平台代码。

## C-09 验证丢失更新、重复副作用和部分失败

对涉及的边界构造具体交错或失败点，核验最终状态、重复请求行为和恢复后再次执行结果。仅测全成功路径或只检查无数据竞争报告不足以证明业务不变量。没有共享并发或多步写入的改动无需新增此类机制。
